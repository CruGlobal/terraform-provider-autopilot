# AGENTS.md

Guidance for coding agents (and people) working in this repository.

## Overview

Terraform provider for AutoPilot's admin API, built on
terraform-plugin-framework (not SDKv2) and published to the Terraform Registry
as `CruGlobal/autopilot`. AutoPilot runs AI agents on work that senders such
as issue trackers send it, and opens pull requests a person reviews. The
provider manages two records: `autopilot_sender` and `autopilot_app`.

Conventional Commits drive release-please (CHANGELOG.md and version bumps),
so commit messages and PR titles matter. The `Validate PR title` check
enforces the allowed types (see `.github/workflows/semantic-pr.yml`).

## This repository is public

Commits, code comments, docs, examples and test fixtures must not carry:

- internal hostnames (use `https://autopilot.example.com` and `example.com`
  names), account ids, project or user ids, work-item keys, chat channels,
  or people's names and email addresses;
- secrets of any kind. Tests make random secrets at run time
  (`randSecret`); never commit a fixed one.

Write docs and comments in plain words, without em dashes.

## Common commands

The project uses [Task](https://taskfile.dev) (`Taskfile.yaml`):

- `task build`: `go build`
- `task vet`, `task lint`: `go vet ./...`, `golangci-lint run` (v2, config in
  `.golangci.yml`; CI pins the version in `ci.yml`)
- `task test`: unit tests against the in-process fake (`go test ./...`);
  needs the terraform CLI, 1.11 or later, on `PATH`
- `task testacc`: the same tests against a live AutoPilot (`TF_ACC=1`,
  `AUTOPILOT_ENDPOINT`, `AUTOPILOT_TOKEN`, optional `AUTOPILOT_ACC_REPOS`)
- `task sweep`: removes the `tfacc-` apps and senders a failed live run left
  behind (the sweepers in `internal/provider/sweep_test.go`)
- `task generate`: regenerates `docs/` with tfplugindocs. CI fails when the
  result differs from what is committed, so run it after any schema,
  description or example change and commit the output.

Run a single test:

```sh
go test -count=1 -run TestSender_rotationByFingerprint ./internal/provider/
```

Tool versions are pinned in `.tool-versions` (asdf); CI's setup-go reads it.

## Layout

```
main.go                     providerserver entrypoint; version set by goreleaser
internal/client/            hand-written admin API client: retries, refusals, records
internal/autopilottest/     in-process fake of the admin API, used by every test
internal/provider/          provider, resources and their tests (one package)
examples/                   Terraform examples that tfplugindocs puts in docs/
docs/                       GENERATED by tfplugindocs; do not edit by hand
tools/                      pins tfplugindocs as a module dependency
```

## The contract

The provider codes to AutoPilot's admin API contract (`docs/admin-api.md` in
AutoPilot's own repository). When the contract changes, change all of these
together: the client (`internal/client`), the fake (`internal/autopilottest`,
which must refuse whatever the real API refuses), the resource, its tests,
the examples, and the generated docs. Things worth knowing:

- Records are keyed by name. A `POST` for a name that already holds the same
  fields answers `200` with the record, so creates are retried freely and no
  `Idempotency-Key` is sent. `client.Adopted` marks a `200` the provider's
  own lost send can't explain. `autopilot_app` refuses it and says to
  import; `autopilot_sender` warns, since its secrets matched too.
- Every `PATCH` and `DELETE` carries `If-Match: "<lock_version>"`. A stale
  update is reported, never retried over. A stale delete re-reads once.
- A change is safe to retry: AutoPilot answers a `PATCH` one version behind,
  whose body the record already holds, with `200`. So a change whose answer
  was lost is simply sent again. `patchRecord` keeps a fallback for an
  AutoPilot that answers such a repeat with `stale_object`: it reads the
  record and takes the change as its own only when the record is one version
  on and holds what it sent.
- The API refuses fields it doesn't know. Send only what is set
  (`SenderSpec` and `AppSpec`: a nil list is not sent, an empty one is sent
  as `[]`), so the provider keeps working against an AutoPilot that predates
  a newer optional field.
- Lists are sets in the schema; the client sends them sorted and without
  repeats, which is how the API keeps them. Values are kept as sent, and a
  `PATCH` replaces a list as sent, so a change of case alone is a change.
  Where a rule says "without regard to case" (repositories), that is how
  AutoPilot compares values and keeps them unique.
- A deleted sender's name and branch prefix are never freed (once it owes
  nothing it is a tombstone). Only a create with the same two secrets and
  the same prefix revives it, at once, at the next `lock_version`, which is
  what `terraform apply -replace` sends. A branch prefix never changes, so
  the sender's `ModifyPlan` replaces the sender for a new prefix only with a
  new name, and refuses one under the same name. Live test runs leave
  tombstones behind; that is expected.
- An app's credential policy (`credential`, `when_seats_full`) is one
  thing: AutoPilot sets both from a write that sends `credential` (a
  `when_seats_full` left out is null) and refuses `when_seats_full` alone.
  The provider sends both on a change to either (`AppSpec.Policy`), and
  `credential: null` to take the policy away.
- An app's worker size (`worker_cpu`, `worker_memory`) is one thing too:
  AutoPilot sets both from a write that sends either, refuses one without
  the other, and takes only the pairs AWS Fargate allows, up to 4 vCPU and
  16 GB (`workerSizes` in `app_validators.go`, checked at plan time). The
  provider sends both on a change to either (`AppSpec.Size`), and both as
  null to take the size away. `worker_image` is sent on its own, as null to
  take the app back to `node`.
- An app's `github_logins` pairs each GitHub login (lowercase, at most 39
  characters) with one of its `developers`. AutoPilot refuses a write that
  sends `developers` or `github_logins` and leaves a pair whose developer
  isn't in `developers`, so the plan checks that (`validateGitHubLogins`),
  and a change to both goes out in one `PATCH`. `developers` and each
  pair's `developer` are checked with AutoPilot's own email rule, step for
  step (`validEmail`, in the provider and the fake).
- An `accepts` entry's `can_decide_own_pr` lets a deciding review decide on
  a pull request that may be the asker's own. AutoPilot takes it only with
  `can_decide = true`, and only for the senders built into it,
  `autopilot-mcp` and `autopilot-github`, whose reviews run for a person
  (`builtInSenders`, checked by `acceptsValidator`). Like `can_auto_merge`,
  it is optional with no default and sent only when true.
- An `accepts` entry's `approve_up_to` is, with `can_decide`, the most risk
  a pull request may carry for that sender's reviews to approve it: `low`,
  `medium` or `high`. AutoPilot takes it only with `can_decide = true`, for
  any sender (checked by `acceptsValidator`), and answers `null` for none.
  It is optional with no default, read back as null when AutoPilot has none,
  and sent only when set.
- An app's `auto_review` is its automatic reviews: AutoPilot reviews its
  pull requests on its own, as the app's service identity, and a GitHub
  Actions workflow listed in `workflows` may ask for one with its OIDC
  token. AutoPilot takes it as one setting, sent whole (a field left out
  is AutoPilot's default, not what was kept), and `null` turns it off. So
  it is a single nested attribute whose fields all have AutoPilot's
  defaults in the schema (`events` `opened` and `ready_for_review`,
  `workflows` none, `max_per_day` 50, the flags false), a change to any
  field sends every one, and removing it sends `null`. The exceptions are
  `gate`, `own_prs` and `bots` (below), and `workflows`, sent sorted and
  each once, and only when it lists some: none is AutoPilot's default, and
  an AutoPilot that predates the field refuses it, so an app that lists
  none still works there. `events` is
  some of `opened`, `ready_for_review` and `synchronize`, kept in that
  order: at least one, unless `workflows` lists one, and set in the
  configuration whenever `workflows` lists one (AutoPilot refuses
  `workflows` without `events`, and the schema's default would hide that
  they were left out). Each workflow is a `job_workflow_ref` on a branch,
  `owner/repo/.github/workflows/<file>.yml@refs/heads/<branch>`, checked
  step for step with AutoPilot's own rule (`parseWorkflowRef` in the
  provider, `workflowKey` in the fake); at most 20, and no two that differ
  only in the case of `owner/repo`. `max_per_day` is 1 to 200; and
  `can_decide_own_pr` and `approve_up_to` come only with `can_decide`.
  `validateAutoReview` checks the rules that span fields. An app that
  leaves it out sends nothing for it, so an older AutoPilot still takes
  the app.
- An app's `auto_review.gate` gives each pull request head its automatic
  reviews take a check run of its own, `AutoPilot review gate`, one a
  ruleset can require: it passes where the review approves, fails where it
  asks for changes or its outcome is `fail`, and otherwise waits until
  someone with write access approves that head. The review's own check
  run, `AutoPilot review (automatic)`, still ends `neutral`, so the docs
  say to require only the gate's. The gate fails closed: where a ruleset
  requires its check, a head without one can't merge, as with the gate off
  or before it was on. So the docs say to turn the gate on only once
  AutoPilot has it, then require the check, and to take the check out of
  the ruleset before turning the gate off.
  AutoPilot takes `true` or `false` (`null` is refused), shows it in every
  `auto_review` (`false` when off), keeps it only when on, and takes `true`
  only with `can_decide` and every event in `events` or a workflow in
  `workflows`, refused at `/auto_review/gate` after the checks of
  `can_decide_own_pr` and `approve_up_to` and before the events'. In the
  schema it is a flag with the default `false`, as `can_decide` is, so an
  answer of `false`, or one without the field, plans nothing. It is sent
  only when `true`, never as `false`: a field left out is AutoPilot's
  default, and an AutoPilot that predates the field refuses it, so an app
  that leaves it off still works there. `validateAutoReviewGate` checks its
  rules at plan time, `can_decide` and `events` left out at their
  defaults. The fake reads it in AutoPilot's sorted order, after `events`
  and before `max_per_day`, and keeps one set from outside a write only
  with `can_decide`, as AutoPilot reads a stored one.
- An app's `auto_review.own_prs` says how the gate's check treats
  AutoPilot's own pull requests, the ones its GitHub App opens for its
  tasks: `wait`, the default, waits for a writer's approval, as for any
  bot's; `pass` passes them with no review, as Dependabot's, so a writer's
  commit pushed onto one passes unreviewed too; and `review` has the
  automatic review review them, and the check goes by that review. GitHub
  refuses a pull request's author an approval, so under `review` AutoPilot
  posts its decision as a comment. AutoPilot takes `wait`, `pass` or
  `review` (anything else, `null` included, is refused at
  `/auto_review/own_prs`), shows it in every `auto_review` (`wait` when
  unset), keeps it only when it isn't `wait`, and takes anything but `wait`
  only with `gate` true, refused at `/auto_review/own_prs` after the gate's
  checks and before the events'. In the schema it is a string with the
  default `wait`, as `gate` is a flag with the default `false`, so an
  answer of `wait`, or one without the field, plans nothing. It is sent
  only as `pass` or `review`, never as `wait`: a field left out is
  AutoPilot's default, and an AutoPilot that predates the field refuses
  it, so an app that leaves it at `wait` still works there.
  `validateAutoReviewOwnPRs` checks its rule at plan time, `gate` left out
  at its default; a `gate` not known yet waits. The fake reads it in
  AutoPilot's sorted order, after `max_per_day` and before `workflows`, and
  keeps one set from outside a write as `pass` or `review` only with the
  gate, and as `wait` otherwise, as AutoPilot reads a stored one.
- An app's `auto_review.bots` lists the bots whose pull requests its
  automatic reviews take, as a person's, gated or not: each the bot's exact
  login as GitHub names a pull request's author, an App's slug and `[bot]`
  (`botLoginPattern`, AutoPilot's own pattern, in the provider and the
  fake), at most 20, and no two that differ only in case
  (`noCaseRepeatsValidator`), all checked at plan time. Listing a bot trusts
  whoever can make it open a pull request: its code runs in the review's
  install and checks, without the Sidekiq Pro key or `review_also_reads`;
  `github-actions[bot]` trusts every writer's workflow; and a listed
  Dependabot is reviewed instead of passing the gate with no review. The
  docs say so plainly, and say never to list an AutoPilot App, this
  environment's or another's: AutoPilot's own pull requests go by
  `own_prs` alone, but it can't tell another environment's App from any
  other bot. AutoPilot refuses its own App's login at
  `/auto_review/bots/<n>` once GitHub has named the App to it, which the
  plan can't know; the fake plays that with `SetOwnAppSlug`. AutoPilot
  keeps the list as sent, sorted and each once, stores it only when it
  lists one, and shows it in every `auto_review` (`[]` for none). In the
  schema it is a set handled as `workflows` is: the default none, so an
  answer of `[]`, or one without the field, plans nothing against a
  configuration that leaves it out or sets `[]`; sent sorted and each once
  only when it lists some, never as `[]`, so an app that lists none still
  works with an AutoPilot that predates the field. The fake reads it in
  AutoPilot's sorted order, after `approve_up_to` and before `can_decide`,
  and keeps a list set from outside a write without the logins that don't
  read, as AutoPilot reads a stored one.
- An app's `review_also_reads` lists other repositories, `owner/name`, that
  the reviews of the app's own repositories also read, read-only. Each is
  checked step for step with AutoPilot's own rule (`validRepo`, in the
  provider and the fake): the owner letters, digits and `-`, at most 39,
  the name letters, digits, `.`, `_` and `-`, at most 100 and not dots
  alone; at most 5, and no two that differ only in case. AutoPilot also
  takes each only of the same owner as one of `repos`, without regard to
  case, and never one of `repos`, on a create and on any change that sends
  either (at `/review_also_reads/<n>` when it sends both, or at
  `/review_also_reads` or `/repos` against the record when it sends one).
  The plan checks that against the configuration
  (`validateReviewAlsoReads`), which is what AutoPilot will hold, so `repos`
  left out is none; a change to both goes out in one `PATCH`. Like `repos`,
  it is optional with no default and null in state while AutoPilot answers
  `[]`. Unlike `repos`, none is never sent, as `auto_review.workflows`
  isn't: it is sent sorted and each once only when it changed and lists
  some, or as `[]` to take some away, never from none to none (null and
  `[]` alike), and an answer without the field reads as none
  (`newerListToSet`). So an app that lists none still works with an
  AutoPilot that predates the field, and one rolled back past it can be
  taken out of the configuration.
- An app's `work_item_projects` lists the work tracker projects, by
  identifier, whose work items the reviews of the app's repositories may
  read when a pull request names one. Each is checked with AutoPilot's own
  pattern (`projectPattern`, in the provider and the fake): a capital
  letter, then capital letters and digits, at most 10; at most 20. It is
  handled as `review_also_reads` is: optional with no default, null in
  state while AutoPilot answers `[]`, sent sorted and each once only when
  it changed and lists some, or as `[]` to take some away, never from none
  to none, and an answer without the field reads as none
  (`newerListToSet`).
- An app's `max_reviews_per_day` is its repositories' daily cap on the
  reviews people ask for from GitHub: 1 to 200, or `null` for AutoPilot's
  default. Like `worker_image`, it is optional with no default, read back
  as null when AutoPilot answers `null` or leaves the field out, sent only
  when set, so an older AutoPilot still takes an app that leaves it out,
  and sent as `null` to take it away (`AppSpec.MaxReviewsPerDay`, 0 for
  null).
- An app's `approve_as_user` lets its reviews approve, on a repository
  where AutoPilot otherwise only comments, by an approval AutoPilot's
  service posts as a separate code owner user. AutoPilot takes `true` or
  `false` (`null` is refused) and answers `false` when it was never set.
  Like an `accepts` entry's `can_auto_merge`, it is optional with no
  default, and off reads back as null unless the configuration says
  `false` (`optionalFlag`). It is sent only when it turns on or off: on a
  create only when `true`, and on a change as `true` or as `false` to turn
  it off, never from off to off (null and `false` alike), so an older
  AutoPilot still takes an app that leaves it off.
- An app's `propose_review_rules` lets AutoPilot open draft pull requests
  that add a rule to the root `REVIEW.md` of the app's repositories, from
  how people answered its review findings, as the app's service identity.
  It works only for a repository AutoPilot's own settings list too. It is
  handled exactly as `approve_as_user` is: AutoPilot takes `true` or
  `false` (`null` is refused) and answers `false` when it was never set;
  optional with no default, off reads back as null unless the
  configuration says `false` (`optionalFlag`); sent on a create only when
  `true`, and on a change as `true` or as `false` to turn it off, never
  from off to off (null and `false` alike). The two flags are sent apart:
  a change to one never sends the other. The fake reads it where
  AutoPilot's sorted order puts it, after `max_reviews_per_day` and before
  `review_also_reads`, except that the fake still reads `repos` first, as
  it does for every field. Its proposals' kind, `propose-review-rules`, is
  one only AutoPilot's service sends: no sender's `kinds` and no `accepts`
  entry may name it.
- An app's `review_model` and `review_effort` are the model and effort of
  AutoPilot's own reviews of the app's repositories (automatic, label,
  command, workflow and MCP; a sender's own `review-pr` tasks name their
  own). `review_model` is a model family, `sonnet` or `opus`, and `null`
  is Sonnet. AutoPilot runs the family's current version, so a new model
  version needs no change here. It refuses Haiku and any versioned name,
  such as `sonnet-5-5`. `review_effort` is `low`, `medium`, `high`,
  `xhigh` or `max`, and `null` is Claude Code's own default for the model.
  They are one choice, as the credential policy is: AutoPilot sets both
  from a write that sends `review_model` (a `review_effort` left out is
  null) and refuses `review_effort` alone, even as `null`. Unlike
  `when_seats_full`, an effort goes with any model, `null` included, so
  the plan checks only each value (`reviewModels` and `reviewEfforts` in
  `app_validators.go`). The provider sends both on a change to either
  (`AppSpec.ReviewModel`): `review_model` always, as `null` for the
  default, and `review_effort` only when set. So removing both sends
  `review_model: null` alone, and an effort alone goes with
  `review_model: null`. Like `max_reviews_per_day`, each is optional with
  no default, read back as null when AutoPilot answers `null` or leaves the
  field out, and neither is sent while both are unset, so an older
  AutoPilot still takes an app that leaves them out. The docs say plainly
  that AutoPilot runs the family's current version, that Sonnet is the
  default, that Opus uses a seat's limits faster and costs more per token
  on Bedrock, and that a higher effort costs more on either. The fake
  reads them where AutoPilot's sorted order puts them, `review_effort`
  then `review_model`, after `review_also_reads` and before
  `when_seats_full`, checks the pair after the worker size, and reads a
  stored model it doesn't run a review on, a versioned name among them, as
  none, its effort dropped with it, and a stored effort it doesn't know as
  none (`storedReviewModel`).
- A sender's `may_send_urgent` lets its tasks be urgent: while AutoPilot's
  limit on running tasks is reached, they start before every queued task
  that isn't, and they don't wait for the day's spend under the daily cap
  on Bedrock spend. AutoPilot takes `true` or `false` (`null` is refused),
  answers `false` when it was never set, and a create or a revival that
  leaves it out sets `false`, so a create matches a sender that has it
  (a retry, or one to take over) only when it sends it too. Like an app's
  `approve_as_user`, it is optional with no default, off reads back as
  null unless the configuration says `false` (`optionalFlag`), and it is
  sent only when it turns on or off: on a create only when `true`, and on
  a change as `true` or as `false` to turn it off, never from off to off
  (null and `false` alike), so an older AutoPilot still takes a sender
  that leaves it off.
- A sender's secrets are write-only (`*_wo`). The plan compares
  `client.Fingerprint` of the configured secrets with the stored
  fingerprints; see the comment at the top of `sender_resource.go`.

## Tests

Every test body runs against the fake by default and against a live
AutoPilot under `TF_ACC`. Tests that need fault injection, writes from
outside Terraform, or the request log call `env.requireFake(t)`. Live tests
make records with random names (`randName`) and must clean up after
themselves; never write a test that needs a particular live record.
